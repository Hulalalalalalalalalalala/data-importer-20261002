# Data Importer

Normalize a CSV file or JSONL stream to JSONL using a small explicit schema. Requires Python 3.10+; no installation dependencies.

`python3 data_importer.py samples/customers.csv --schema samples/schema.json --output customers.jsonl --errors errors.jsonl` converts the two valid CSV rows. The input format is chosen explicitly with `--format csv` (default) or `--format jsonl`; it is never inferred from the file extension. For JSONL, use `python3 data_importer.py samples/customers.jsonl --schema samples/schema.json --output customers.jsonl --errors errors.jsonl --format jsonl`. `samples/mixed.csv` and `samples/mixed.jsonl` each contain one accepted row and two rejected rows. Each rejected row is written separately with its physical line number (for CSV the header is line 1) and its errors; accepted rows remain available in input order.

Schema columns specify name, type (`string`, `integer`, `boolean`) and optional `required`. A column may also declare an optional `source`: the CSV column, or JSONL object key, it reads from, while `name` remains the output field name; omitting `source` reads the field named by `name`. An explicit `source` must be a non-empty, non-blank string, and the effective source names must be unique across columns (a source may coincide with another field's `name`, and two fields may swap sources). For CSV the header must match the effective source names and their order exactly, compared literally without trimming or case folding. For JSONL each non-empty line must hold exactly one JSON object whose key set equals the effective source set exactly (order is free, keys match literally); missing or extra keys reject the line.

CSV text is trimmed, absent optional values become JSON null, and booleans accept true/false without case sensitivity. A column may declare an optional `default` holding a value of the column's target type: for `string` it must be a JSON string whose trimmed form is non-empty (the trimmed form is what gets written); for `integer` a non-boolean JSON integer (0 is valid); for `boolean` a JSON boolean (false is valid). Null, arrays, objects and any other value not matching the declared type are schema configuration errors: the API raises `ValueError` (naming both the output field and the offending default) before the input file is opened, and the CLI exits 2 with its usual JSON `error` on standard output, leaving both output files untouched (previously absent files stay absent). When a default is declared, a value that is empty after the existing whitespace handling (CSV) or a JSON null / trimmed-to-empty string (JSONL) is filled with the default instead of following the required/null rule — a `required` column may be filled this way. Non-empty values still convert under the ordinary type rules, and an illegal non-empty value is reported as a field error rather than masked by the default. Defaults never relax structural validation (CSV headers and cell counts, JSONL key sets and duplicate keys are checked exactly as before; a missing JSONL key is not supplied by a default), and the schema object passed to the API is never modified. Filled values are the final record values used everywhere downstream, so `filter_eq` and `duplicate_by` see them too (an empty cell and the input string `"3"` both become integer 3 when `default` is 3, match the same filter and group as duplicates). Columns without a default keep the exact previous required/empty behavior. No default-related count is added to the result or CLI summary. JSONL is read as UTF-8, allowing a leading byte-order mark; blank lines are skipped while still consuming a physical line number, and an empty or all-blank file reports zero counts. Each line is parsed independently: invalid JSON, a non-object top-level value, duplicate top-level keys, and the `NaN`, `Infinity` and `-Infinity` constants reject that line and later lines are still processed. String values are trimmed; trimmed-to-empty strings and JSON null follow the same required/null rule as CSV. The `string` type accepts JSON strings only; `integer` accepts non-boolean JSON integers or strings convertible under the CSV rule (fractional and exponential JSON numbers are rejected); `boolean` accepts JSON booleans or case-insensitive `true`/`false` strings. Arrays, objects and any other value never convert implicitly and are reported as field errors. Error messages distinguish parse, structure and field errors; field errors use the output field name and are collected in schema order. Output objects use sorted keys. The input is processed in memory. Outputs replace existing files but cannot alias either input or each other; parent output directories must already exist and are never created. The two outputs commit together: on a successful run both the records and errors files are fully written (serialised into temporary files in each target's own directory, then swapped into place), while a filesystem failure (a target that is a directory, a missing or unwritable parent, an unwritable target path, or a write error) leaves both targets exactly as they were beforehand — pre-existing files keep their bytes and previously absent files stay absent. CLI exit codes are 0 for no rejected rows, 1 for row errors and 2 for an invalid format or configuration (including mapping, header or key-set mismatches), unreadable input, or other I/O errors; in that case standard output carries only a JSON object with a non-empty `error` string naming the failing target path (no success summary) and existing output files are left untouched (and absent ones are not created).

`normalize_csv` and `normalize_jsonl` accept an optional `duplicate_by` keyword: a non-empty list of output field names compared across accepted records using their trimmed, type-converted values (so integer `3` matches the string `"3"`; strings stay case-sensitive; nulls match nulls). Field names match schema `name` literally, never `source`. When enabled, the result adds a `duplicates` array; omitting the option or passing `None` leaves the result unchanged. Each group appears only when a key occurs more than once, as `{"key": {field: value, ...}, "record_numbers": [1, 4, ...]}`, where record numbers are one-based positions in `records` (rejected rows and blank JSONL lines do not count), groups are ordered by first occurrence and numbers ascend within a group. No record is removed or rejected for duplication; `accepted`, `rejected` and the exit code reflect validation only. Invalid configuration (not a list, empty list, non-string or blank entries, repeats, unknown fields) raises `ValueError` naming the offending entry before the input is read. On the CLI, repeat `--duplicate-by FIELD` once per field, in order; with bad configuration the command exits 2 with a JSON `error` on standard output and creates or overwrites neither output file. The CLI summary gains `duplicates` only when the flag is present.

Both functions also accept an optional `filter_eq` keyword holding one equality condition, `{"field": NAME, "value": VALUE}`, and the CLI accepts the same object as a JSON string via `--filter-eq` (for example `--filter-eq '{"field": "active", "value": true}'`). Every record is fully validated and converted before the filter is applied: invalid rows still enter `errors` with their physical line numbers and are never hidden by a non-matching condition, while valid records that simply fail the predicate leave `records` out and are not counted as rejected. The condition has exactly two keys, `field` and `value`; `field` matches a schema `name` literally and case-sensitively — `source` aliases are not recognized — and must be a non-blank string. `value` is never converted or trimmed and must already fit the target field type: a string for `string` columns (case-sensitive, exact), a non-boolean integer for `integer` columns, and a boolean for `boolean` columns; `null` is allowed for every type and matches only normalized empty values. When filtering is enabled the result adds `filtered` (the number of valid rows removed by the predicate) and `accepted` equals the number of kept records; kept records stay in input order and the blank-line rules are unchanged. With `duplicate_by` enabled together, duplicates are computed over the kept records only and `record_numbers` restart at 1 in kept order. If every valid row is filtered out the records export is an empty file; the exit code is still 0 without row errors and 1 with them. Omitting the option, passing `None`, or omitting the CLI flag leaves the result structure and behavior exactly as before (no `filtered` key). The API rejects non-objects, missing or extra keys, non-string or blank fields, unknown fields and values of the wrong type with `ValueError` (naming `filter_eq` or its field) before the input is read; the CLI exits 2 for invalid JSON, a non-object condition, or any such configuration error, printing only a JSON object with a non-empty `error` string and creating or overwriting neither output.

The public API is `normalize_csv(source, schema, duplicate_by=None, filter_eq=None)` and `normalize_jsonl(source, schema, duplicate_by=None, filter_eq=None)`, each returning records, errors, counts and, when enabled, duplicates. JSONL file-open failures raise `OSError` and undecodable bytes raise `UnicodeDecodeError`. `write_jsonl(path, records)` persists either sequence with deterministic serialization. Run `python3 -B -m unittest -v` for API conversion and CLI checks.
