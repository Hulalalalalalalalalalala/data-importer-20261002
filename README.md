# Data Importer

Normalize a CSV file or JSONL stream to JSONL or CSV using a small explicit schema. Requires Python 3.10+; no installation dependencies.

`python3 data_importer.py samples/customers.csv --schema samples/schema.json --output customers.jsonl --errors errors.jsonl` converts the two valid CSV rows. The input format is chosen explicitly with `--format csv` (default) or `--format jsonl`; it is never inferred from the file extension. The records output format is chosen independently with `--output-format jsonl` (default) or `--output-format csv`; it too is never inferred from the extension, and `--format` and `--output-format` may name different formats (for example JSONL input with CSV output). For JSONL input, use `python3 data_importer.py samples/customers.jsonl --schema samples/schema.json --output customers.jsonl --errors errors.jsonl --format jsonl`; add `--output-format csv` to write the normalized records as CSV instead. `samples/mixed.csv` and `samples/mixed.jsonl` each contain one accepted row and two rejected rows. Each rejected row is written separately with its physical line number (for CSV the header is line 1) and its errors; accepted rows remain available in input order.

The records output is JSONL unless `--output-format csv` is given. JSONL output is one sorted-key object per line exactly as before. CSV output is UTF-8 with no byte-order mark, comma-delimited, and every line ends in LF — the header and every data record alike, including the last. The header names the output fields by their schema `name` in the declared order of `schema.columns`, never their `source` aliases, and follows the same quoting rule as data; data rows follow kept-record order after filtering. Cell serialization is: integers as decimal text, booleans as lowercase `true`/`false`, null as an empty cell, and strings as their normalized content with any interior newline characters retained (a CR embedded in a value stays a CR even though record terminators are LF). A cell containing a comma, a double quote, a CR or an LF is wrapped in double quotes and each interior double quote is doubled; all other cells stay unquoted. An empty cell stays bare, except in a single-column table where it is written as a quoted empty string (`""`) so the record cannot be mistaken for a skipped blank line. As long as the import does not fail outright, the header is written even when no record is kept (all records filtered out, or every row rejected); the same normalized Chinese, special-character and null samples produce byte-identical CSV whether imported from CSV or JSONL. The errors output is always JSONL, in every output format. Validation, missing-value handling, filtering, duplicate reporting, the summary fields on standard output and the exit-code meanings are unchanged by the output format. An invalid `--output-format` exits 2 after the path-isolation check but before either input file or the schema is read: standard output carries only a JSON object whose non-empty `error` string contains `output-format` and the offending value verbatim (no success summary), and neither output is created or overwritten; when both `--format` and `--output-format` are invalid the output-format error is reported. The CSV records output commits together with the JSONL errors output under the existing all-or-nothing rules: a records target that is a directory, a missing or unwritable parent on either side, an unwritable target, or a write failure exits 2 with an `error` naming the failing path, pre-existing outputs keep their bytes, previously absent outputs stay absent, no directory is created, and the input and schema files are untouched.


Schema columns specify name, type (`string`, `integer`, `boolean`), optional `required`, and an optional target-typed `default` (see below). A column may also declare an optional `source`: the CSV column, or JSONL object key, it reads from, while `name` remains the output field name; omitting `source` reads the field named by `name`. An explicit `source` must be a non-empty, non-blank string, and the effective source names must be unique across columns (a source may coincide with another field's `name`, and two fields may swap sources). For CSV the header must match the effective source names and their order exactly, compared literally without trimming or case folding. For JSONL each non-empty line must hold exactly one JSON object whose key set equals the effective source set exactly (order is free, keys match literally); missing or extra keys reject the line.

CSV text is trimmed, absent optional values become JSON null, and booleans accept true/false without case sensitivity. CSV quote syntax is checked strictly for both the header and every data record: two double quotes inside a quoted field still denote one literal double quote, and a double quote inside an unquoted field stays an ordinary character, but a quoted field that is still open when the file ends, or any character other than a comma, a line ending or the end of the file appearing immediately after a closing quote (a space or tab included), aborts the whole parse rather than being folded into the cell value. `normalize_csv` raises `ValueError` whose message contains "CSV parse error", the input path, the offending record's starting physical line and a reason distinguishing the two problems (the header starts at line 1; a data record starts on the physical line after the preceding read record ends, so blank lines and newlines inside quoted fields shift it, and an error detected only on a later line or at EOF still points at the record start); no partial result is returned. On the CLI (the default format or explicit `--format csv`) such an error exits 2 with standard output carrying only a JSON object whose non-empty `error` string carries that message (no success summary), and both outputs keep their pre-run state — existing files keep their bytes, previously absent files are not created, and the input and schema are untouched — regardless of valid records or ordinary row errors read earlier. (Ordinary per-row errors — type, required, enum or cell-count problems — still leave other rows valid and exit 1; quote-syntax failures are the only CSV parse errors that abort the run.) JSONL is read as UTF-8, allowing a leading byte-order mark; blank lines are skipped while still consuming a physical line number, and an empty or all-blank file reports zero counts. Each line is parsed independently: invalid JSON, a non-object top-level value, duplicate top-level keys, and the `NaN`, `Infinity` and `-Infinity` constants reject that line and later lines are still processed. String values are trimmed; trimmed-to-empty strings and JSON null follow the same required/null rule as CSV. The `string` type accepts JSON strings only; `integer` accepts non-boolean JSON integers or strings convertible under the CSV rule (fractional and exponential JSON numbers are rejected); `boolean` accepts JSON booleans or case-insensitive `true`/`false` strings. Arrays, objects and any other value never convert implicitly and are reported as field errors. Error messages distinguish parse, structure and field errors; field errors use the output field name and are collected in schema order. Output objects use sorted keys. The input is processed in memory. Outputs replace existing files but cannot alias either input or each other; this is checked before either input is read or either output is written. Identity ignores file names, extensions and directories: two paths alias when they resolve to the same pathname (identical paths, relative or absolute, including symbolic links) or, when both currently exist, when they are the same file on disk (the same device and inode, so two distinct names hard-linked to one file alias it); two independent files with identical contents are not aliases. An output that does not exist yet only takes part in the resolved-pathname comparison. An alias conflict exits 2 with standard output carrying only a JSON object whose non-empty `error` string names the paths that point to the same file (no accepted/rejected summary); the source, schema and both outputs stay exactly as they were — existing files keep their bytes, hard-link relationships and symbolic links themselves are untouched, and absent outputs are not created. Parent output directories must already exist and are never created. The two outputs commit together: on a successful run both the records and errors files are fully written (serialised into temporary files in each target's own directory, then swapped into place), while a filesystem failure (a target that is a directory, a missing or unwritable parent, an unwritable target path, or a write error) leaves both targets exactly as they were beforehand — pre-existing files keep their bytes and previously absent files stay absent. CLI exit codes are 0 for no rejected rows, 1 for row errors and 2 for an invalid format or configuration (including mapping, header or key-set mismatches), unreadable input, an alias conflict, or other I/O errors (including a path that cannot be resolved or stated); in that case standard output carries only a JSON object with a non-empty `error` string naming the failing target path (no success summary) and existing output files are left untouched (and absent ones are not created).

A column may declare an optional `default` written as a value of the target type: `string` defaults must be strings whose trimmed value is non-empty (the trimmed value is what gets emitted), `integer` defaults must be non-boolean integers, and `boolean` defaults must be booleans (`0` and `false` are valid). `null`, arrays, objects and anything else not matching the declared type — including a blank string — is a configuration error: the API raises `ValueError` (naming both `default` and the output field) before the input is read, even when no row would have needed it, and the CLI exits 2 with only a JSON `error` object on standard output, leaving both output files exactly as they were (absent ones stay absent); the caller's schema object is never mutated. When a declared default applies, a CSV cell that is empty after trimming or a JSONL value that is JSON null or trims to empty is filled with the processed default instead of following the required/null rule — `required` columns may be filled this way in both formats. A non-empty value still converts under the ordinary type rules and an illegal non-empty value is reported as a field error exactly as before; the default never masks it. Defaults do not relax structural validation: the CSV header and cell count, and the JSONL key set and duplicate-key rules are unchanged, so a missing key or cell cannot be defaulted into a valid record. The filled value is the final value used everywhere downstream, so `filter_eq` and `duplicate_by` see it (an empty cell and the input `"3"` both become integer `3` with `default: 3`, match a `filter_eq` of 3, and group together). Columns without `default` keep the previous required and empty-value behavior in full; no default statistics are added to the result and its optional keys appear only when filtering or duplication is enabled.

A column may declare an optional `allowed_values` list restricting its legal converted values: it must be a non-empty list whose elements already have the column's target type — strings for `string` columns (kept verbatim, never trimmed or case folded), non-boolean integers for `integer` columns, booleans for `boolean` columns; `null`, arrays and objects are never valid elements, and repeated elements judged by value equality (exact string equality) make the configuration invalid. A malformed attribute (wrong type, an empty list, a wrong-typed element, or a repeat) is a configuration error: the API raises `ValueError` naming both `allowed_values` and the output field (element errors also name the offending element, and an attribute-level error names the attribute value) before the input is read, and the CLI exits 2 with only a JSON `error` object on standard output, leaving both output files exactly as they were (absent ones stay absent); the caller's schema object is never mutated. Each row is still structurally checked, type-converted and handled for empty values exactly as before; the enum match runs on the non-null result only — an optional empty value with no default still emits `null` regardless of the list, and a required empty value still reports its ordinary error. A non-empty value that fails conversion reports only the original type error (no enum error is added); a value that converts successfully but is not in the list rejects the whole row with a field error naming the output field and `allowed_values`, while later rows are still processed. Field errors from several columns are collected in schema order and physical row numbers are unchanged; enum membership never repairs a structural error (header/cell count or key-set/duplicate-key violations). A processed `default` outside `allowed_values` is the same configuration error even when no input row would use the default, so it is rejected before the input is read. Enum validation runs before `filter_eq`: an enum-invalid row always reaches `errors` and is never hidden by filtering, while `duplicate_by` still counts only the records left after filtering. With `orders` an integer column declaring `allowed_values: [0, 3]` and `default: 3`, an empty cell and the string `"3"` both become integer `3`, `0` is kept, `4` produces the enum error, and `"bad"` produces only the integer type error; the CSV and JSONL results agree on the fixed offline samples (apart from each format's own physical row numbering and pre-existing type-error wording). Columns without `allowed_values`, and older callers, behave exactly as before: no new result keys, statistics, exit-code changes, switches, files or output formats are introduced.

`normalize_csv` and `normalize_jsonl` accept an optional `duplicate_by` keyword: a non-empty list of output field names compared across accepted records using their trimmed, type-converted values (so integer `3` matches the string `"3"`; strings stay case-sensitive; nulls match nulls). Field names match schema `name` literally, never `source`. When enabled, the result adds a `duplicates` array; omitting the option or passing `None` leaves the result unchanged. Each group appears only when a key occurs more than once, as `{"key": {field: value, ...}, "record_numbers": [1, 4, ...]}`, where record numbers are one-based positions in `records` (rejected rows and blank JSONL lines do not count), groups are ordered by first occurrence and numbers ascend within a group. No record is removed or rejected for duplication; `accepted`, `rejected` and the exit code reflect validation only. Invalid configuration (not a list, empty list, non-string or blank entries, repeats, unknown fields) raises `ValueError` naming the offending entry before the input is read. On the CLI, repeat `--duplicate-by FIELD` once per field, in order; with bad configuration the command exits 2 with a JSON `error` on standard output and creates or overwrites neither output file. The CLI summary gains `duplicates` only when the flag is present.

Both functions also accept an optional `filter_eq` keyword holding one equality condition, `{"field": NAME, "value": VALUE}`, and the CLI accepts the same object as a JSON string via `--filter-eq` (for example `--filter-eq '{"field": "active", "value": true}'`). Every record is fully validated and converted before the filter is applied: invalid rows still enter `errors` with their physical line numbers and are never hidden by a non-matching condition, while valid records that simply fail the predicate leave `records` out and are not counted as rejected. The condition has exactly two keys, `field` and `value`; `field` matches a schema `name` literally and case-sensitively — `source` aliases are not recognized — and must be a non-blank string. `value` is never converted or trimmed and must already fit the target field type: a string for `string` columns (case-sensitive, exact), a non-boolean integer for `integer` columns, and a boolean for `boolean` columns; `null` is allowed for every type and matches only normalized empty values. When filtering is enabled the result adds `filtered` (the number of valid rows removed by the predicate) and `accepted` equals the number of kept records; kept records stay in input order and the blank-line rules are unchanged. With `duplicate_by` enabled together, duplicates are computed over the kept records only and `record_numbers` restart at 1 in kept order. If every valid row is filtered out the records export is an empty file; the exit code is still 0 without row errors and 1 with them. Omitting the option, passing `None`, or omitting the CLI flag leaves the result structure and behavior exactly as before (no `filtered` key). The API rejects non-objects, missing or extra keys, non-string or blank fields, unknown fields and values of the wrong type with `ValueError` (naming `filter_eq` or its field) before the input is read; the CLI exits 2 for invalid JSON, a non-object condition, or any such configuration error, printing only a JSON object with a non-empty `error` string and creating or overwriting neither output.

Both functions also accept an optional `deduplicate_by` keyword: a non-empty list of output field names (independent of `duplicate_by`, which may be used alongside it) selecting keep-first deduplication of the valid records. Field names match schema `name` literally and case-sensitively — names are never trimmed and `source` aliases are not recognized — and the list must have no repeats. Processing order is fixed: every row is first validated and converted exactly as before, then `filter_eq` is applied, and only the surviving valid records are deduplicated, so invalid rows still enter `errors` with their physical line numbers unchanged and are never hidden or removed as duplicates. Two records are duplicates only when the final value of *every* named field is equal: strings compare case-sensitively, integer/boolean values compare after conversion, and null equals null. For each group the first record in input order is kept complete — differing non-key fields are never merged or overwritten — and the remaining records keep their relative order. When enabled the result adds `deduplicated`, the number of valid records dropped as repeats (0 when nothing repeats or nothing survives the filter); `accepted` is the final number of records after both filtering and deduplication, `rejected` still counts only invalid rows, and `filtered` (when filtering is enabled) counts only predicate removals. A `duplicate_by` report used together is computed over the final deduplicated records, with `record_numbers` restarting at 1 in final-record order and groups ordered by first occurrence. Invalid configuration (not a list, an empty list, a non-string or blank entry, a repeat, or an unknown field) raises `ValueError` naming both `deduplicate_by` and the offending value before the input is read; the caller's list and schema are never mutated. Omitting the option or passing `None` leaves the result exactly as before with no new key. On the CLI repeat `--deduplicate-by FIELD` once per field; the summary gains `deduplicated` only when the flag is present, bad configuration exits 2 with only a JSON `error` object on standard output and creates or overwrites neither output (existing files keep their bytes, absent ones stay absent), and a normal run still exits 1 with row errors and 0 without them. With two columns `name` and `orders`, the converted sequence `("A",3)`, `("A",3)`, `("B",3)`, `("A",4)`, `("B",3)` (in JSONL the second `3` may arrive as the string `"3"`) deduplicating by both columns keeps the first, third and fourth records — `accepted` 3 and `deduplicated` 2 in both CSV and JSONL — and an additional illegal `orders` row adds exactly one `rejected`.

A column may declare an optional `missing_values` list of text markers that count as missing: it must be a non-empty list of strings, each trimmed of surrounding whitespace, and the trimmed markers must be non-empty and unique (compared case-sensitively). A malformed attribute (not a list, an empty list, a non-string entry, a blank entry, or a repeat after trimming) is a configuration error: the API raises `ValueError` naming `missing_values`, the output field and the offending value before the input is read, and the CLI exits 2 with only a JSON `error` object on standard output, leaving both output files exactly as they were (absent ones stay absent); the caller's schema object is never mutated. A marker only matches a trimmed input string in full, case-sensitively, before any type conversion; a hit then follows the ordinary empty-value flow — a declared `default` fills it, a `required` column reports its usual required error, and an optional column emits `null`. The default itself is never matched against the markers and is still checked against `allowed_values` as before. In JSONL only JSON strings take part in marker matching: numbers, booleans, arrays and objects are never stringified for the comparison, and JSON null and the empty string keep their existing semantics; a non-empty value that matches no marker converts under the ordinary type rules. Structural validation is unchanged and stays prior: a marker cannot fill a missing CSV cell or JSONL key, and it does not mask extra keys, duplicate keys or CSV quote-syntax errors. Field errors are still collected in schema order into `errors`, reject the whole row, keep their physical row numbers and do not stop later rows; filtering and the duplicate report see the final post-marker values, so with `orders` an integer column declaring `missing_values: ["N/A"]`, `default: 3` and `allowed_values: [0, 3]`, the inputs `" N/A "` and `"3"` both become integer `3`, `0` stays `0`, `4` produces the enum error, `"bad"` produces the integer type error, and declaring `"n/a"` does not match `"N/A"`. Columns without `missing_values`, older callers, `write_jsonl` and the existing export formats, exit codes, path isolation and dual-output commit behavior are unchanged: no new result keys, statistics, switches, files or output formats are introduced.

A `boolean` column may declare an optional `boolean_aliases` object mapping extra non-empty text to booleans, for example `{"是": true, "否": false, "YES": true}`. The attribute is allowed only on `boolean` columns, must be a non-empty object, every key must be a string that trims to non-empty text, and every mapped value must be a JSON boolean. Two keys that coincide after trimming and Unicode case folding are a configuration error even when they map to the same boolean, and a normalized key equal to the built-in `true` or `false` is refused so the built-in spellings cannot be overridden. A malformed attribute (declaring it on another type, a non-object or empty object, a non-string or blank key, a non-boolean value, a folded duplicate, or a key folding to `true`/`false`) is a configuration error: the API raises `ValueError` naming `boolean_aliases`, the output field and the offending value before the input is read and after the existing schema structure check, and the CLI exits 2 with only a JSON `error` object on standard output, leaving both output files exactly as they were (absent ones stay absent); the caller's schema object is never mutated. Alias keys and input strings are both trimmed of surrounding whitespace and compared by Unicode case folding, so the key `"YES"` matches `" yes "`; the built-in `true`/`false` spellings are still accepted by their original case-insensitive rule. In JSONL a native boolean is preserved verbatim, while numbers, arrays and objects keep their original boolean field error — only strings take part in alias matching. `missing_values` markers and empty values are handled first exactly as before: a marker hit still goes through the `default`, `required` or null flow (a boolean default must still be a native boolean), and an empty value never reaches alias lookup. Non-empty text that matches neither an alias nor a built-in spelling rejects the whole row into `errors` with the original `boolean must be true or false` wording, its physical row number and the usual schema-order field errors, while later rows are still processed. A converted alias is an ordinary boolean from then on: `allowed_values` is checked after conversion, followed by `filter_eq`, deduplication and the duplicate report. With `active` declaring `boolean_aliases: {"是": true, "否": false, "YES": true}`, the inputs `" 是 "`, `"否"`, `"yes"` and `"未知"` convert to `true`, `false`, `true` plus one rejected row in both CSV and JSONL (`accepted` 3, `rejected` 1); filtering on `active` equal to `true` then gives `accepted` 2 and `filtered` 1, and the duplicate report by `active` points at positions 1 and 2. Columns without `boolean_aliases`, older callers, `write_jsonl` and the existing export formats, exit codes, path isolation and dual-output commit behavior are unchanged: no new result keys, statistics, switches, files or output formats are introduced.

An `integer` column may declare optional inclusive range bounds `minimum` and `maximum`: either end may be set alone, equal ends accept exactly that one integer, and omitting both keeps the previous behavior. Each bound must be a non-boolean integer — negative values and zero are legal — and declaring a bound on a `string` or `boolean` column, a null/string/float/boolean bound, or a `minimum` greater than the `maximum` is a configuration error: the API raises `ValueError` naming the output field, the attribute and the offending value before the input is read, and the CLI exits 2 with only a JSON `error` object on standard output, leaving both output files exactly as they were (absent ones stay absent); the caller's schema object is never mutated. A processed `default` outside the declared range is the same configuration error even when no record would use it. Each row is still structurally checked, marker-matched, defaulted and type-converted exactly as before, then checked against `allowed_values`, and only then is a non-null integer compared with the bounds: an optional empty value stays `null`, a required empty value keeps its ordinary error, and a conversion or enum failure keeps only its original error. An `allowed_values` entry that lies outside the range is not a configuration error, but a record converting to it still fails the range check. An out-of-range integer rejects the whole row into `errors` with a field error naming the output field, the actual integer, the violated `minimum` or `maximum` and the bound value, while later rows are still processed; errors from several columns are collected in schema order and physical row numbers are unchanged. Range validation runs before `filter_eq`: an out-of-range row counts as `rejected`, never as `filtered`, and `duplicate_by` still counts only the records left after filtering. With `orders` an integer column declaring `minimum: 0`, `maximum: 5`, `default: 3` and `missing_values: ["N/A"]`, the inputs `"0"`, `"3"`, `"5"`, `"-1"`, `"6"`, `"bad"` and `" N/A "` yield the integers `0`, `3`, `5`, `3` with `accepted` 4 and `rejected` 3 (`-1` and `6` fail the range, `"bad"` keeps only its type error); filtering on `orders` equal to `3` then gives `accepted` 2 and `filtered` 2, and the duplicate report over the kept records points at positions 1 and 2. Columns without bounds, older callers, `write_jsonl` and the existing export formats, exit codes, path isolation and dual-output commit behavior are unchanged: no new result keys, statistics, switches, files or output formats are introduced.

An `integer` column may declare an optional `lte_field` naming another `integer` column by its output `name`: the column's final integer must not be greater than the target column's final integer, and equality is legal. The reference matches output names literally (a `source` alias cannot stand in) and its direction is independent of declaration order — the target may be declared before or after the referencing column. The attribute must be a non-blank string naming a different `integer` column; a non-string, a blank string, an unknown field, a self reference, a non-integer target, or declaring `lte_field` on a `string` or `boolean` column is a configuration error: the API raises `ValueError` naming `lte_field`, the output field and the attribute value before the input is read, and the CLI exits 2 with only a JSON `error` object on standard output, leaving both output files exactly as they were (absent ones stay absent); the existing schema structure check still runs first and the caller's schema object is never mutated. Each row is still structurally checked, marker-matched, defaulted, type-converted and checked against `allowed_values` and the range bounds exactly as before, and only then are the final integers compared: when either final value is null, or either participating field already carries a required, type, enum or range error, that relation is skipped and its original error is kept verbatim (no relation error is added), while every other relation on the row is still checked. A violating integer rejects the whole row into `errors` with a field error naming `lte_field`, both output names and the two actual integers (the local value and the target value); relation errors are attributed to their declaring column and collected together with the field errors in schema column order, physical row numbers are unchanged, and later rows are still processed. A filled `default` is a final value like any other, so a default standing in a violated relation is an ordinary row error rather than a configuration error; no cross-field default check is added. Relation validation runs before `filter_eq`: a violating row counts as `rejected`, never as `filtered`, and `duplicate_by` still counts only the records left after filtering. With two optional integer columns `lo` and `hi` where `lo` declares `lte_field: "hi"`, the five records `(1, 3)`, `(4, 3)`, `(null, 3)`, `(2, 2)` and `("bad", 3)` (an empty CSV cell expresses null) give `accepted` 3 and `rejected` 2 in both CSV and JSONL — the first error is the relation error on `(4, 3)` and the second is the original integer type error on `("bad", 3)`, in that order. Columns without `lte_field`, older callers, `write_jsonl` and the existing export formats, exit codes, path isolation and dual-output commit behavior are unchanged: no new result keys, statistics, switches, files or output formats are introduced.

The schema itself is structurally validated before the data file is opened, identically by `normalize_csv` and `normalize_jsonl`: it must be an object holding a non-empty `columns` list, each column must be an object carrying `name` and `type`, `name` must be a non-blank string that is used verbatim (never trimmed) and is unique case-sensitively, `type` must be one of `string`, `integer` or `boolean`, and `required` — optional, treated as false when omitted — must be a boolean when present. Any violation raises `ValueError` before the input is read; the message names `schema` and the error location with one-based column numbers, names a missing `name`/`type` key, carries the offending value verbatim, and points a duplicate name at the later column. Checks run top level first, then column by column in order (column structure, name, duplicate name, type, required) and only the first problem is reported. Unknown attributes are ignored and the caller's schema object is never mutated. On the CLI such a configuration error exits 2 with standard output carrying only a JSON object whose non-empty `error` string holds the message (no success summary); existing outputs keep their bytes, absent outputs stay absent, and the input and schema files are untouched — the path-alias precheck still runs first. The `source`, `default` and `allowed_values` validations described above apply after this structural check, and valid schemas behave exactly as before in both formats.

The public API is `normalize_csv(source, schema, duplicate_by=None, filter_eq=None, deduplicate_by=None)` and `normalize_jsonl(source, schema, duplicate_by=None, filter_eq=None, deduplicate_by=None)`, each returning records, errors, counts and, when enabled, duplicates and/or deduplication counts. JSONL file-open failures raise `OSError` and undecodable bytes raise `UnicodeDecodeError`. CSV export is a CLI-only addition: the signatures and result structures of both normalizers, and the JSONL export behavior of `write_jsonl(path, records)`, are unchanged. `write_jsonl(path, records)` persists either sequence with deterministic serialization. Run `python3 -B -m unittest -v` for API conversion and CLI checks.
